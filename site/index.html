  2. Ward

    Open source · Rust CLI

    GitHub repository settings as code. Describe what you want in a ward.toml, then plan, apply and verify it across many repositories at once. Because clicking through the same settings page a hundred times is no way to live.

    I built it for a team with many repositories and no admin rights that wanted every repo on the same GitHub standards, without click-ops. So I took the Terraform idea, config-driven desired state, to repository settings.

    v0.6.2 · latest · 15 Oct 2026github.com/OriginalMHV/Ward
    • brew install OriginalMHV/tap/ward-cli
    • ward import OWNER/REPOwrite ward.toml from an existing repository
    • ward planshow what differs from GitHub, change nothing
    • ward applyapply one category at a time, then verify it
    • ward driftfor CI: exits 0 in sync, 1 drift, 2 could not run

    Declarative GitHub repository management. Plan, apply, verify.

  3. minimenta

    Rust · TUI

    An interactive disk usage analyzer for the terminal. It looks and feels like ncdu, scans faster, and lets you select many items and move them to the Trash in one step. Find what fills your disk, and let it go.

    The name is Latin: minuere impedimenta, reduce the baggage. Impedimenta was the baggage train of a Roman army. Install with brew install OriginalMHV/tap/minimenta and run mm.

Smaller, safer, easier

At Telenor, since 2022

A better engineer always aims to simplify and remove code, especially now. AI is great, but it has its limits, and it's easy to be blind to how much legacy you create with it.

ASmaller

Less to run, less to break.

  1. A1

    Fewer services

    Retired old applications and repositories. Fewer services means fewer pipelines, secrets, alerts and late-night surprises.

  2. A2

    One less vendor

    Wrote most of a new integration that replaced a paid data vendor with open public data.

  3. A3

    Old systems, new homes

    Moved services from legacy infrastructure to Kubernetes, and helped lead the move from Atlassian to GitHub.

BSafer

Fewer ways for things to go wrong.

  1. B1

    Real data out of test

    When real customer data had to leave the test environments, the fear was simple: no data to test end to end. I co-built a synthetic test data platform, so teams could keep testing. Privacy is a design requirement, not a checkbox.

  2. B2

    Migrations that land

    Built the integration layer for an email platform migration, and have driven framework and runtime upgrades across many services since, most recently to Spring Boot 4 and Java 25. The scariest one so far had an app so flaky it would stop if you looked at it wrong.

  3. B3

    Safe by default

    Rolled out shared CI/CD, security scanning and repository standards, so the right choice is also the easy one.

CEasier

I like building the rails other people run on.

  1. C1

    An onboarding site for developers

    I created our developer onboarding site: the docs I wish existed when I started. New developers start there now. I still maintain it, and newcomers add to it too.

  2. C2

    A dashboard other teams adopted

    I built a repository health dashboard to track my own upgrade work: security alerts, versions and open pull requests. Other teams saw it and started using it.

  3. C3

    AI as a team tool

    I build shared AI skills that know our standards, so the whole team benefits, not just me. I also co-created an interview where candidates use AI to modernize a legacy service.
